# قوانین حیاتی - باید رعایت شوند

## پاسخ‌ها
- پاسخ‌ها را کوتاه و دقیق نگه دارید - مگر اینکه کاربر درخواست دیگری داشته باشد.

## حالت برنامه‌ریزی
- همیشه سوالات شفاف‌کننده بپرسید.
- هرگز در مورد طراحی، پشته فناوری (tech stack) یا ویژگی‌ها فرض نکنید.
- از ساب‌اجنت‌های (sub-agents) تخصصی برای کمک به تحقیق استفاده کنید.
- قبل از ارائه برنامه به کاربر، از ساب‌اجنت‌ها برای بررسی جنبه‌های مختلف برنامه استفاده کنید.
💡

## حالت تغییر / ویرایش
- تا حد امکان خودتان ویژگی‌ها را پیاده‌سازی نکنید - از ساب‌اجنت‌ها استفاده کنید!
- تغییرات نسبت به برنامه اصلی را که می‌توانند به صورت موازی اجرا شوند شناسایی کنید و برای پیاده‌سازی کارآمد ویژگی‌ها از ساب‌اجنت‌ها کمک بگیرید.
- هنگام استفاده از ساب‌اجنت‌ها برای پیاده‌سازی ویژگی‌ها، فقط به عنوان هماهنگ‌کننده عمل کنید.
- برای هر کار از بهترین مدل استفاده کنید - مدل‌های پیشرفته برای کارهای پیچیده (مانند کدنویسی) و مدل‌های سطح متوسط برای کارهای ساده‌تر (مانند مستندسازی).

# قوانین و دستورالعمل‌های پروژه HikStatus

## قوانین کلی
- کامیت‌ها همیشه با توضیحات فارسی انجام شوند
- از مرورگر برای تست یا دیباگ فقط در صورت درخواست استفاده شود
- از `.env` برای secrets استفاده شود، هرگز هاردکد نشوند
- لاگ‌های ترمینال به انگلیسی
- خطاهای Web UI به فارسی
- دستورالعمل‌ها و مستندات به فارسی
- تمامی تاریخ‌ها و زمان‌ها در رابط کاربری وب (UI) و گزارش‌ها باید به صورت شمسی و با زبان فارسی نمایش داده شوند با فرمت: `پنج‌شنبه ۲۵ تیر ۱۱:۴۵`

## قوانین تغییرات بنیادی
ساختار بنیادی پروژه در `Structure.md` تعریف شده است. همیشه در آن طرح بمانید.
اگر رفع باگ یا قابلیت جدید نیاز به تغییر بنیادی دارد، توضیح دهید و اجازه بگیرید.

## قوانین Git
- پیام commit به فارسی
- هر commit فقط تغییرات مرتبط با یک موضوع را شامل شود
- برای هر کار، ابتدا کدنویسی را انجام داده و مستندات مربوطه (مانند فایل‌های مستندات و لیست مشکلات) را بروزرسانی کنید، سپس همه را با هم در قالب یک کامیت ثبت کنید (از چند کامیت مجزا برای کد و داکیومنت خودداری کنید)
- قبل از commit، حتماً `git status` و `git diff` بررسی شود
- هرگزsecrets ها commit نشوند
